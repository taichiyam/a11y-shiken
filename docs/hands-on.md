# ハンズオン: 10 分で 1 ページ検査して結果を読む

初めて a11y-shiken を触る人が、**インストールから「最初の 1 ページを検査して、結果を読む」まで**を一本道で辿るためのガイドです。

検査対象には、このプロジェクトが公開しているダミーサイト（実在しない施設のサイト）を使います。
自分のサイトを用意する必要はありません。手順どおりに進めれば、このガイドに載せたものと同じ形のレポートが手元に出ます。

| 手順 | 内容 | 目安 |
|---|---|---|
| [1](#1-前提を確認する) | 前提を確認する | 1 分 |
| [2](#2-インストールする) | インストールする | 1 分 |
| [3](#3-最初の-1-ページを検査する) | 最初の 1 ページを検査する | 3 〜 5 分 |
| [4](#4-出力を読む) | 出力を読む | 3 分 |
| | **ここまでで約 10 分** | |
| [5](#5-複数ページをまとめて検査する) | 複数ページをまとめて検査する（発展） | + 5 〜 10 分 |
| [6](#6-適合版と比べる) | 適合版と比べる（発展） | + 5 分 |
| [7](#7-つまずいたら) | つまずいたら | — |

> **このガイドに載せている件数は、2026-08-25 に実行した一例です。**
> 55 項目のうち一部は生成 AI が判定しており、判定を試みる範囲は実行ごとに変わりえます。
> 同じ URL でも件数が数件ずれることがありますが、それ自体は異常ではありません。

---

## 検査対象について

このガイドでは、次の 2 つを使います。どちらも GitHub Pages で公開されている静的サイトです。

| URL | 内容 |
|---|---|
| https://taichiyam.github.io/a11y-shiken-demo-site/ng/ | **違反を仕込んだ版**（このガイドで検査するのはこちら） |
| https://taichiyam.github.io/a11y-shiken-demo-site/ok/ | 同じサイトの**適合版** |

どちらも「つばめ台コミュニティセンター」という架空の施設のサイトで、トップページ・施設案内・お問い合わせ・お知らせ一覧・写真ギャラリーの 5 ページ構成です。
実在の施設・団体とは関係ありません。このガイドの CSV では最初の 3 ページを使いますが、慣れたら news.html / gallery.html を足して試せます。

自分で実行せず出力だけ先に見たい場合は、トップ・施設案内・お問い合わせの 6 ページ（ok / ng 各 3 ページ）を検査した結果一式が [examples/site-report/](../examples/site-report/) にあります。

## 1. 前提を確認する

必要なのは [Claude Code](https://claude.com/claude-code) と [bun](https://bun.sh/docs/installation) の 2 つだけです。

```bash
claude --version
bun --version
```

どちらもバージョンが表示されれば準備完了です。

- `bun: command not found` の場合 → [bun のインストール手順](https://bun.sh/docs/installation)に従って導入し、**ターミナルを再起動**してください
- Node.js は不要です（bun に内包されています）
- Playwright の Chromium は、初回の検査実行時に自動でインストールされます。ここで用意する必要はありません

対応環境は macOS 14+ / Ubuntu 22.04+ です。Windows のネイティブ環境は未検証です。

---

## 2. インストールする

npm には公開していません。GitHub リポジトリから直接導入します。

```bash
npx skills add taichiyam/a11y-shiken
```

カレントのプロジェクトにスキルが入ります。自分の環境すべてで使いたい場合は `--global` を付けます。

```bash
npx skills add taichiyam/a11y-shiken --global
```

`/plugin` で更新まで管理したい場合は、Claude Code の plugin marketplace からも入れられます。

```
/plugin marketplace add taichiyam/a11y-shiken
/plugin install a11y-shiken@a11y-shiken
```

**起動コマンドは導入方法で変わります。**

| 導入方法 | 起動 |
|---|---|
| `npx skills add` | `/a11y-shiken` |
| plugin marketplace | `/a11y-shiken:a11y-shiken` |

以降このガイドでは `/a11y-shiken` と書きます。marketplace から入れた場合は読み替えてください。

## 3. 最初の 1 ページを検査する

検査結果は**カレントディレクトリの `docs/a11y-test/` 配下**に書き出されます。
出力先を汚したくない場合は、先に作業用ディレクトリを作ってそこで Claude Code を起動してください。

```bash
mkdir -p ~/a11y-handson && cd ~/a11y-handson
claude
```

Claude Code の中で、次の 1 行を入力します。

```
/a11y-shiken https://taichiyam.github.io/a11y-shiken-demo-site/ng/
```

### 聞かれること

出力するレポート形式を 1 度だけ聞かれます。

```
出力するレポート形式を選択してください
  1. Excel（.xlsx）のみ — ディレクター・PM向け。一覧表で全体の対応状況を把握
  2. Markdownレポートのみ — 開発者向け。修正箇所の詳細・コードスニペット付き
  3. 両方（デフォルト）— Excel + Markdown
```

**このハンズオンでは「両方」を選んでください。** 手順 4 で 3 種類の出力を順に読むためです。

### 何が起きるか

選択したあとは、次の順で自動的に進みます。ページ内容の入力は不要です。

| | 処理 | 実測時間（1 ページ） |
|---|---|---|
| 1 | **axe-core による自動チェック** — 機械的に検出できる違反を洗い出す | 約 4 秒 |
| 2 | **Visual テスト** — ターゲットサイズ・非テキストのコントラストなどを Playwright で確認 | 約 3 秒 |
| 3 | **Interactive テスト** — キーボード操作・フォーカス可視化・リフローなどを実際に操作して確認 | 約 9 秒 |
| 4 | **アクセシビリティツリーの取得** — レンダリング後の構造を取り出す | 約 3 秒 |
| 5 | **生成 AI（Claude）による判定** — 機械で埋まらなかった項目を、ツリーと HTML を読んで判定する | 数十秒 〜 数分 |
| 6 | **Excel・Markdown・基本17項目ビューの生成** | 1 秒未満 |

**スクリプトの実行そのものは合計 20 秒ほどです。** 待ち時間の大半は 5 の生成 AI 判定で、ここは実行環境と応答速度に左右されます。
体感では **1 ページあたり 2 〜 4 分**を見ておいてください。

> **初回だけ長くかかります。** 1 の前に、検査スクリプトの依存パッケージ（exceljs / playwright）の自動インストール（数秒 〜 数十秒）と、
> Playwright の Chromium のダウンロード（回線次第で数分）が入ります。2 回目以降はどちらもキャッシュされるため発生しません。

### 出てくるもの

完了すると、次の構成でファイルが出力されます（実行時のタイムスタンプとドメイン名がディレクトリ名に入ります）。

```
docs/a11y-test/20260825010933_taichiyam-github-io/
├── report/                                            ← 人が読む側
│   ├── a11y-checklist-taichiyam-github-io-2026-08-25.xlsx
│   ├── index.html                                     ← サイドバー付き HTML ビューア
│   ├── index.md
│   └── markdown/
│       ├── _index.md                                  ← 概要・ページ別サマリー
│       ├── ng.md                                      ← 55 項目の詳細レポート
│       └── ng-baseline-17.md                          ← 基本17項目ビュー
└── data/                                              ← 証跡（生 JSON・スクリーンショット）
    ├── manifest.json
    └── ng/
        ├── axe-result.json
        ├── visual-result.json
        ├── interactive-result.json
        ├── a11y-tree.txt
        ├── claude-overrides.json
        ├── merged-result.json                         ← 55 項目の最終判定
        ├── baseline-17.json
        └── screenshots/
```

`data/` は「なぜその判定になったか」を後から追うための証跡です。最初は `report/` だけ見れば十分です。

> ファイル名の `ng` はページのラベルです。URL だけを渡した場合はパスから自動導出されるため、手元では別の名前になることがあります。
> 手順 5 のように CSV でラベルを指定すると、その名前がそのまま使われます。

## 4. 出力を読む

`report/` の 3 種類は、**同じ 1 回の検査結果を、読む人ごとに切り出したもの**です。数字は必ず一致します。

### 4-1. HTML ビューア — まず「どこから直すか」を見る

`report/index.html` をブラウザで開きます。**ダブルクリックするだけで表示されます。**サーバーの起動は必要ありません。

```bash
open docs/a11y-test/20260825010933_taichiyam-github-io/report/index.html
```

左サイドバーからページを選ぶと、右ペインにレポートが表示されます。

このファイルは Markdown 本文も描画用ライブラリもすべて 1 ファイルに埋め込まれているため、オフラインでも表示でき、単体で他の人に渡すこともできます。

**このビューから読み始めます。** WCAG 2.2 の 55 項目をそのまま渡されても、どれが致命的でどれが後回しでよいかは判断できません。
基本17項目ビューは、55 項目の判定結果をデジタル庁『ウェブアクセシビリティ導入ガイドブック』の 17 項目に集約したものです。

実測では、こういう表が出ます。

```
| | 件数 |
|---|---|
| ❌ 要修正 | 8 |
| ⚠️ 一部未確認（目視が必要な基準が残っている） | 6 |
| ✅ 確認OK | 3 |
```

```
| # | 項目 | 状態 | 内訳 |
|---|---|---|---|
| 5 | 画像に代替テキストを付与する | ❌ 要修正 | 1基準中 **不適合 1** |
| 6 | キーボードだけで全機能にアクセスできる | ❌ 要修正 | 5基準中 確認 2 / **不適合 1** / 未確認 2 |
| 11 | 文字と背景に十分なコントラスト比 | ❌ 要修正 | 1基準中 **不適合 1** |
| 15 | リンクを適切に表現する | ❌ 要修正 | 1基準中 **不適合 1** |
```

**❌ が付いた項目から読みます。** 表の下に項目ごとの内訳があり、どの達成基準がどう判定されたかと、その根拠が書かれています。

たとえば項目 15「リンクを適切に表現する」の内訳には、達成基準 2.4.4 が「不適合」（判定元: 自動判定(Claude)）として並び、
備考にこう書かれています。

```
「こちら」だけのリンクが複数あり、リンクテキスト単独では目的が判別できない;
証拠: a11y-tree: - link "こちら": /url: facility.html#rooms、
- link "こちら": /url: facility.html#hours、- link "こちら": /url: contact.html
```

**「証拠:」以降が、そう判定した根拠です。** ページ上のどの要素を見てそう言っているかが書かれているので、
判定に納得できない場合はここを見て反証できます。

生成 AI の判定は、**証拠を書けなかった時点で統合スクリプトが機械的に「未確認」へ降格します。**
プロンプトの言いつけではなくコードの分岐で担保しているため、**根拠なしの「確認OK」がこの表に出ることはありません。**

### 4-2. 「未確認」の意味 — ここが一番重要です

上の実測では、55 項目の内訳は **確認OK 18 / 修正あり 9 / 未確認 28** でした。
**未確認が半分を占めます。これは検査の失敗ではありません。**

「未確認」は、**このツールが確認できなかったことを、確認できなかったまま出している**状態です。次のどれかに当たります。

| 未確認になる理由 | 例 |
|---|---|
| 人が見ないと判断できない | 2.3.1（光の点滅）、1.4.1（色だけで情報を伝えていないか） |
| 検査はあるが、達成基準の一部しか見ていない | 1.4.4（テキストサイズ変更）— 縦方向の切れは見るが、重なり・可読性は見ていない |
| 1 ページ単位の検査では埋まらない | 3.2.3（一貫したナビゲーション）— ページ間の比較が必要 |
| 生成 AI が証拠を引けなかった | 2.2.1（制限時間）— 静的なツリーからは判断できない |

**このツールは、確認できていないものを「確認OK」に混ぜません。**
17 項目に集約するときも、不適合が無くても未確認が残っていれば「⚠️ 一部未確認」のままにします。多数決や平均で「確認OK」に丸めることはしません。

間違った不合格は、直そうとした人が「これは問題ない」と気づいて現場で止まります。
間違った合格は、検査済みとして扱われて誰も見に行きません。**未確認の件数が多いのは、この非対称性を優先した結果です。**

判定の仕組みそのものは [判定の仕組みの詳細](how-it-works.md) にまとめてあります。

### 4-3. Excel — ディレクターに渡す

`report/a11y-checklist-{ドメイン}-{日付}.xlsx` を開きます。

| シート | 内容 |
|---|---|
| **まとめ** | ページごとの件数一覧（確認OK / 修正あり / 未確認 / 合計）と、詳細シートへのリンク |
| **{ラベル}** | そのページの 55 項目チェックシート |

詳細シートの列はこうなっています。

```
| No. | カテゴリ | チェック項目 | 達成基準 | レベル | 確認内容 | 担当 | 結果 | 備考 |
```

**「担当」列が、そのまま作業分担になります。**

| 担当 | 意味 | 次にやること |
|---|---|---|
| 自動判定 | axe-core が判定 | 開発側で修正 |
| 自動判定(Visual) / (Interactive) | Playwright の操作で判定 | 開発側で修正 |
| 自動判定(Claude) | 生成 AI がツリー・HTML を読んで判定 | 備考の証拠を確認してから修正 |
| **要目視確認** | 判定できなかった | **人が手で確認する** |

「要目視確認」の行がそのまま**残作業のチェックリスト**になります。Excel をそのまま渡して、確認担当と期限を書き込んでもらう使い方を想定しています。

### 4-4. Markdown — 開発者として直す

`report/markdown/ng.md` を開きます。構成は 3 つです。

1. **サマリー** — 修正あり / 確認OK / 未確認 の件数
2. **チェック項目** — 55 項目の一覧表（Excel の詳細シートと同じ内容）
3. **修正が必要な項目の詳細** — 「修正あり」の項目だけを展開したセクション

直すときは 3 を上から見ます。実測では、このページの「修正あり」9 件の内訳はこうなりました。

| 達成基準 | 検出内容 | 判定元 |
|---|---|---|
| 1.1.1 非テキストコンテンツ | 画像の代替テキストが `alt="画像"` で、内容を説明していない | Claude |
| 1.3.1 情報及び関係性 | 見出しが h1 の次に h3 へ飛んでいる | Claude |
| 1.4.3 コントラスト（最低限） | 文字と背景のコントラスト比が不足（3 箇所） | axe-core |
| 2.4.1 ブロックスキップ | ランドマークもスキップリンクも無い | Claude |
| 2.4.4 リンクの目的 | 「こちら」だけのリンクが複数 | Claude |
| 2.4.7 フォーカスの可視化 | フォーカスインジケータが確認できない要素がある | Interactive |
| 3.1.1 ページの言語 | `<html>` に `lang` 属性が無い | Claude |
| 3.1.2 一部分の言語 | 日本語ページ内の英文に `lang` 属性が無い | Claude |
| 4.1.2 名前・役割・値 | 検索ボタンにアクセシブルな名前が無い（中の svg が `aria-hidden`） | Claude |

各項目の備考に、**どの要素のどの属性がそうなっているか**が書かれています。そこを直します。

> **このツールは自動で修正しません。** 直し方の提案はレポートに書きますが、適用するかどうかの判断は人に残しています。
> 判定を保守側に倒す設計と、コードを自動で書き換える機能は相性が悪いためです。

## 5. 複数ページをまとめて検査する

実際のサイトは 1 ページでは終わりません。`ラベル,URL` 形式の CSV を渡すと、まとめて検査できます。

作業ディレクトリに `urls.csv` を作ります。**次の内容をそのまま貼り付ければ動きます。**

```csv
TOP,https://taichiyam.github.io/a11y-shiken-demo-site/ng/
施設案内,https://taichiyam.github.io/a11y-shiken-demo-site/ng/facility.html
お問い合わせ,https://taichiyam.github.io/a11y-shiken-demo-site/ng/contact.html
```

- ヘッダー行は不要です
- 1 列目のラベルは Excel のシート名・出力ディレクトリ名になります。日本語で構いません
- ラベルを省いて URL だけ 1 列で書くこともできます（その場合はドメイン・パスから自動導出されます）

Claude Code で CSV のパスを渡します。

```
/a11y-shiken urls.csv
```

レポート形式を聞かれたあと、**ページごとに手順 3 と同じ処理が順に走ります。** 3 ページなら実測時間もおよそ 3 倍です（体感 6 〜 12 分）。

出力は 1 つのディレクトリにまとまります。

- `report/a11y-checklist-*.xlsx` — 「まとめ」シートに 3 ページ分の件数が並び、各詳細シートへリンクが張られる
- `report/markdown/{ラベル}.md` — ページごとに 1 ファイル
- `report/index.html` — サイドバーから 3 ページを切り替えられる

> **ページ間の比較が必要な達成基準（3.2.3 一貫したナビゲーション / 3.2.4 一貫した識別性 / 3.2.6 一貫したヘルプ）は、複数ページを渡しても自動では埋まりません。**
> 検査は 1 ページ単位で完結する設計のためです。これらは「未確認」のまま残ります。

## 6. 適合版と比べる

同じサイトの適合版を検査すると、判定がどう変わるかを見られます。

```
/a11y-shiken https://taichiyam.github.io/a11y-shiken-demo-site/ok/
```

適合版のトップページでは、**axe-core の違反が 0 件**になります（違反版は 3 ルール・5 箇所を検出。いずれも 2026-08-25 実測）。
違反版で ❌ 要修正 だった基本17項目も、対応する違反が取り除かれている分だけ ❌ が外れます。

**それでも「全部 ✅ 確認OK」にはなりません。** 目視でしか判定できない項目・検査が達成基準の一部しか見ていない項目は、
違反が無くても「未確認」のまま残るためです。手順 4-2 で書いた設計がそのまま現れます。

**適合版で見るのは「✅ が並ぶこと」ではなく「❌ 要修正 が 0 件になること」です。**

## 7. つまずいたら

### `bun: command not found` で止まる

bun が入っていないか、PATH が通っていません。[bun のインストール手順](https://bun.sh/docs/installation)に従って導入し、**ターミナルを再起動**してから再実行してください。
インストール直後の同じシェルでは PATH が更新されていないことがあります。

### 最初の 1 回だけ、いつまでも終わらない

Playwright の Chromium を初回にダウンロードしているためです。回線次第で数分かかります。2 回目以降は発生しません。
待てない場合は、手順 2 でスキルが配置されたディレクトリの `scripts/` で手動インストールもできます（配置先は `npx skills add` の出力に表示されます）。

```bash
cd <スキルの配置先>/a11y-shiken/scripts && bunx playwright install chromium
```

### 対象サイトに繋がらない / タイムアウトする

まず素の HTTP で届くか確認します。

```bash
curl -I https://taichiyam.github.io/a11y-shiken-demo-site/ng/
```

`200` が返らない場合はネットワーク側の問題です。プロキシ環境・社内ネットワークからの接続を確認してください。

`200` は返るのに検査が失敗する場合は、次を確認します。

- **Basic 認証つきの環境・自己署名証明書の環境には、現時点で対応していません**（[制限事項](../README.md#制限事項)）
- ログインが必要なページも対象外です
- ページの描画に時間がかかる SPA では、描画完了前に検査が走ることがあります

### `report/index.html` を開いても何も表示されない

`index.html` は Markdown も描画用ライブラリもすべて埋め込んだ単一ファイルなので、`file://` で開けばそのまま表示されます。オフラインでも動きます。

それでも表示されない場合は、生成が途中で失敗している可能性があります。`report/markdown/*.md` は独立したファイルとして残っているので、そちらを直接開けば内容は読めます（VSCode の Markdown プレビューでも読めます）。
検査をやり直す場合は、`bun scripts/generate-report-html.ts` の実行時にエラーが出ていないかを確認してください。

### 「未確認」が多すぎて結果が使えないように見える

設計どおりです。手順 4-2 を読んでください。確認できていない範囲がそのまま見えている状態で、検査の失敗ではありません。
