# a11y-shiken は何をどう判定しているのか

このドキュメントは、a11y-shiken が WCAG 2.2 Level A + AA の 55 項目をどう判定しているかを、実装にもとづいて説明します。

想定読者は次の 2 種類です。

- 導入を検討している開発者・ディレクター（何が自動で終わり、何が手作業として残るのかを知りたい）
- 判定結果を信用してよいか疑っている人（どこまでが機械検証で、どこからが推測なのかを知りたい）

**先に結論を書きます。**

- 55 項目のうち、**19 項目は自動検査（axe-core / Visual / Interactive）だけでは「確認OK」になりません。** 検査が存在しないか、存在しても合格を出さない設計だからです
- 生成 AI（Claude）の判定は、**証拠を引用できなかった時点でコードが機械的に「未確認」へ降格します。** プロンプトの言いつけではなく、統合スクリプトの分岐で担保しています
- それでも、**根拠の薄い「確認OK」は残っています。** 後半の[既知の限界](#known-limits)に、実測で確認できたものを隠さず挙げました

以下の記述は、リポジトリ内の実装（`skills/a11y-shiken/scripts/` 配下）を読んで確認できた内容だけで構成しています。

## 1. 判定パイプラインの全体像

1 つの URL に対して、次の順で処理が進みます。

```
URL
 │
 ├─(1) axe-core 検査        scripts/a11y-test.ts            → axe-result.json
 ├─(2) Visual 検査          scripts/a11y-visual-test.ts     → visual-result.json
 ├─(3) Interactive 検査     scripts/a11y-interactive-test.ts→ interactive-result.json
 ├─(4) a11y ツリー取得      scripts/a11y-tree.ts            → a11y-tree.txt
 │
 ├─(5) 生成 AI 判定         Claude（SKILL.md ステップ5）     → claude-overrides.json
 │
 ├─(6) 統合                 scripts/generate-checklist-xlsx.ts
 │                                          → merged-result.json（55項目の最終判定）
 │                                          → a11y-checklist-*.xlsx
 │
 └─(7) 17項目集約           scripts/generate-baseline-view.ts
                                            → baseline-17.json / *-baseline-17.md
```

(1)〜(4) はいずれも Playwright の Chromium を起動し、`scripts/lib/stable-browser.ts` の同じ読み込み手順（`load` 待ち → networkidle の best-effort 待機 → 全ページスクロールで遅延読み込みを発火 → Web フォント待ち → アニメーション凍結 CSS 注入 → 固定 1 秒待機）を通ります。実行ごとに結果がぶれないようにするためです。

| 工程 | スクリプト | 入力 | 出力 | 内容 |
|---|---|---|---|---|
| (1) axe-core 検査 | `a11y-test.ts` | URL | `axe-result.json` | axe-core を WCAG タグ（`wcag2a` / `wcag2aa` / `wcag21a` / `wcag21aa` / `wcag22a` / `wcag22aa`）で実行し、`violations` / `incomplete` / `passes` を出力 |
| (2) Visual 検査 | `a11y-visual-test.ts` | URL | `visual-result.json` | ページを読み込んだ状態の DOM・computed style・CDP のイベントリスナー情報を使う 15 チェック |
| (3) Interactive 検査 | `a11y-interactive-test.ts` | URL | `interactive-result.json` | キーボード送出・ビューポート変更・ズームなど、操作しないと分からない 9 チェック |
| (4) a11y ツリー取得 | `a11y-tree.ts` | URL | `a11y-tree.txt` | `page.locator("body").ariaSnapshot()` でレンダリング後のアクセシビリティツリーをテキスト化 |
| (5) 生成 AI 判定 | Claude（スクリプトではない） | `a11y-tree.txt`（なければ WebFetch した HTML） | `claude-overrides.json` | 機械検査で埋まらなかった項目を判定 |
| (6) 統合 | `generate-checklist-xlsx.ts` | 上記 4 つの JSON | `merged-result.json` / Excel | 55 項目の最終判定を決定 |
| (7) 17項目集約 | `generate-baseline-view.ts` | `merged-result.json` | `baseline-17.json` / Markdown | デジタル庁の基本 17 項目へ集約 |

`merged-result.json` が唯一の正です。Excel も Markdown レポートも、このファイルを表示形式に変換しているだけなので、両者の結果が食い違うことはありません。

### 検査は 1 ページ単位です

(1)〜(6) はすべて 1 つの URL について完結します。複数 URL を渡した場合もページごとに独立して判定し、**ページをまたいだ比較は一切行いません。** これは 3.2.3（一貫したナビゲーション）・3.2.4（一貫した識別性）・3.2.6（一貫したヘルプ）を自動判定できない直接の理由です。

## 2. 判定の 3 値がどう決まるか

内部では 4 つの状態を持ち、表示は 3 値に畳まれます（`generate-checklist-xlsx.ts` の `getDisplayLabel()`）。

| 内部状態 | 表示 | 意味 |
|---|---|---|
| 適合 | ✅ 確認OK | 検査が根拠をもって問題なしと判断した |
| 不適合 | 🔴 修正あり | 検査が問題を検出した |
| 要確認 | ⚠️ 未確認 | axe-core が `incomplete`（機械では判断しきれない）と返した |
| 目視確認 | ⚠️ 未確認 | どの検査も判定に至らなかった |

「要確認」と「目視確認」は由来が違うだけで、表示上はどちらも「未確認」です。

### 出発点は axe-core です

`evaluateCriterion()` が、55 項目それぞれに紐づけた WCAG タグ（例: 1.1.1 なら `wcag111`）で axe-core の結果を引き当てます。

1. `violations` に一致するルールがある → **不適合**
2. `incomplete` に一致するルールがある → **要確認**
3. `passes` に一致するルールがある → **適合**
4. どれにも一致しない → **目視確認**

**4 が既定値です。** axe-core にその基準を扱うルールが存在しない場合も、ルールはあるがページに該当要素がなく実行されなかった場合も、ここに落ちます。

### 「未確認」に倒れるのは次の場合です

- その基準を扱う自動検査が最初から存在しない（例: 2.3.1 閃光）
- 検査は存在するが、検証範囲が達成基準の一部にとどまるため合格を出さない設計になっている（例: 2.4.7 フォーカスの可視化、1.4.11 非テキストのコントラスト、4.1.3 ステータスメッセージ）
- 検査が対象要素を見つけられなかった、または実行に失敗した（CDP 接続失敗、タイムアウト等）
- 生成 AI が判定したが、**証拠を書けなかったため機械的に降格された**（後述）
- axe-core が `incomplete` を返した（背景画像の上のテキストのコントラストなど）

## 3. 結果の統合ルール

`mergeResults()` が、4 つのソースを次の順で重ねます。

```
axe-core（土台） → 生成AI判定 → Visual検査 → Interactive検査（最優先）
```

後から重なるものが優先ですが、無条件の上書きではありません。実際に効いている制約は 3 つあります。

### (a) warning は上書きしない

Visual / Interactive の結果が `warning` の場合、統合はその基準に触れません（`check.result !== "warning"` の条件で弾いています）。生成 AI の `warning` も判定を変えません。ただし、その時点の判定が「要確認」か「目視確認」であれば、AI が書いた懸念点を備考に引き継ぎます。

**この仕様には副作用があります。** 下位の axe-core がすでに「適合」を出していると、上位の専用検査が「合格とは言えない」と判断しても、結果は「確認OK」のまま残ります。実例は[既知の限界](#known-limits)に挙げました。

### (b) 不適合 → 適合 の降格は、証拠がある場合しか通さない

`applyOverrideStatus()` の遷移ルールです。

| 遷移 | 扱い |
|---|---|
| 適合 → 不適合 | 無条件で許可 |
| 任意 → 未確認 | そもそも上書きしない（(a) の通り） |
| **不適合 → 適合** | **上書き側に証拠がある場合のみ許可** |

証拠とは、生成 AI なら `evidence` フィールド、Visual / Interactive なら `details` フィールドです。空文字・欠落なら降格は却下され、**先に出ていた「不適合」が維持されます。**

安全側（合格→不合格）への遷移は自由に、危険側（不合格→合格）への遷移は制限する、という非対称な設計です。

### (c) 矛盾は必ず記録に残す

「不適合 → 適合」を試みた基準には、**上書きが通ったか却下されたかを問わず** `conflict: true` が立ち、備考に経緯が残ります。

- 通った場合: `⚠️ 判定矛盾: {前の判定元}の不適合を{上書き元}が適合で上書き`
- 却下された場合: `⚠️ 判定矛盾: {上書き元}は適合と判定したが、証拠がないため{前の判定元}の不適合を維持`

この記述は Excel の備考列にもそのまま出力されます。Markdown レポートでも要約・削除せず残す運用です（`SKILL.md` ステップ5.7）。検査結果を読む人が「ツールの中で意見が割れた箇所」を後から追えるようにするためです。

### axe-core の 1 ルールが複数基準にまたがる場合

axe-core のルールは複数の WCAG タグを持つことがあります（例: `link-name` は `wcag244` と `wcag412` の両方）。統合はタグ単位で引き当てるため、**該当するすべての基準に同じ結果が反映されます。**

## 4. 生成 AI（Claude）判定の仕組み

### どの項目を AI が判定するか

固定の担当リストはありません。`SKILL.md` のステップ5 で、Claude が次の観点について判定を試み、結果を `claude-overrides.json` に書きます。

**アクセシビリティツリーから判定する項目**

- 2.4.4 リンクテキストの品質（ツリー上のアクセシブルネームを直接確認する）
- 2.4.1 ランドマークの有無（`banner` / `main` / `navigation` / `contentinfo`）
- 1.3.1 見出し階層
- 4.1.2 `aria-hidden` による誤った隠蔽（ツリーから要素が欠落しているかで判別）
- 1.3.1 / 4.1.2 フォーム要素のアクセシブルネーム

**ツリーに現れないため HTML から判定する項目**

- 3.1.1 / 3.1.2 lang 属性
- 1.4.5 文字画像
- 1.2.x 音声・映像要素の有無と代替
- 2.2.2 CSS アニメーションの一時停止手段
- 1.4.13 ホバー / フォーカスで表示されるコンテンツ
- 2.2.1 時間制限付きコンテンツ
- 2.4.1 スキップリンク

### AI に渡す入力

| 優先度 | ソース | 条件 |
|---|---|---|
| 1 | `a11y-tree.txt` | 工程 (4) が成功している場合 |
| 2 | WebFetch した HTML の部分抽出 | ツリーが空、または工程 (4) が失敗した場合 |

ツリーを優先するのは、精度とコストの両方の理由からです。`ariaSnapshot()` の出力は支援技術が実際に受け取る構造そのもので、`aria-label` などは解決済みの値が入ります。JS 実行後の状態なので SPA でも正しく取れます。HTML 全文より大幅に小さいので入力トークンも抑えられます。

実際の出力は次の形式です（YAML 風のインデント）。

```
# アクセシビリティツリー
URL: https://example.com
取得日時: 2026-08-20T05:37:54.412Z

- link "本文へスキップ":
  - /url: "#main"
- banner:
  - paragraph:
    - link "つばめ台コミュニティセンター":
      - /url: ./
  - search:
    - text: サイト内検索
```

フォールバック時の HTML 抽出範囲は `<head>` 全体、`<nav>` / `<header>` / `<footer>`、`<main>` の先頭 200 行程度、すべての `<form>` / `<audio>` / `<video>`、`<a>` タグ最大 50 件です。

### 証拠必須ガード — 信頼性の要

生成 AI の判定は、そのままでは「もっともらしいが根拠のない合格」を生みます。それを機械的に潰しているのが `sanitizeClaudeOverrides()` です。

```ts
// 証拠必須ガード: evidence が空・欠落の pass / fail / not-applicable を warning（未確認）に強制降格する。
// not-applicable も「確認OK」として出力されるため、pass と同様に証拠を要求する
```

動作は単純です。

1. `claude-overrides.json` の各判定を見る
2. `status` が `warning` なら何もしない
3. そうでなければ `evidence` が空文字・空白のみ・欠落でないかを調べる
4. 証拠がなければ `status` を `warning` に書き換え、`details` の先頭に `【証拠なしのため未確認に降格（元判定: pass）】` を付ける
5. 降格した事実をログに出す

重要なのは **`not-applicable`（該当コンテンツなし）も証拠を要求される** ことです。`not-applicable` は最終的に「確認OK」として集計されるため、pass と同じ扱いにしています。「このページに動画はありません」と言うだけでは通らず、「a11y-tree 全体に audio/video 要素が存在しない」のように、ツリーや HTML から引ける事実を書く必要があります。

この降格はプロンプトの指示ではなく統合スクリプトの分岐です。**AI が指示を無視して証拠なしの合格を出しても、最終結果には反映されません。** AI の判定が信用できるかどうかを、AI 自身の自己申告に頼らない構造にしてあります。

なお、これは「証拠が書かれていること」の検査であって、「証拠が正しいこと」の検査ではありません。AI が実在しないセレクタを証拠として書いた場合、ガードは素通りします。ここは現時点で未対策です。

## 5. 各基準が何を検証し、何を検証していないか

「判定担当」は、その基準に対して実行されうる自動検査です。実際にどれが最終結果になるかは、第 3 章の統合ルールで決まります。

### 1. 知覚可能

| 基準 | レベル | 判定担当 | 実際に検証していること | 検証していないこと |
|---|---|---|---|---|
| 1.1.1 非テキストコンテンツ | A | axe / AI | `image-alt` `input-image-alt` `object-alt` `role-img-alt` `svg-img-alt` 等で alt・アクセシブルネームの有無 | alt の内容が画像を適切に説明しているか（AI が判定を試みる） |
| 1.2.1 音声のみ及び映像のみ | A | axe / AI | `audio-caption` が `<audio>` の存在時にキャプショントラックの有無を見る | 代替テキスト・代替メディアの内容。要素がなければ axe は実行されず未確認 |
| 1.2.2 キャプション（収録済） | A | axe / AI | `video-caption` が `<video>` の存在時にキャプショントラックの有無を見る（`<track kind="captions">` があれば pass） | **キャプションの正確さ・同期。トラックが1つ付いているだけで適合になります** |
| 1.2.3 音声解説又は代替 | A | **なし** | — | 全部。AI 判定か目視のみ |
| 1.2.4 キャプション（ライブ） | AA | **なし** | — | 全部 |
| 1.2.5 音声解説（収録済） | AA | **なし** | — | 全部 |
| 1.3.1 情報及び関係性 | A | axe / Visual / AI | axe: リスト・定義リスト・テーブルの `th`/`caption`/`headers`、ARIA の必須親子関係。Visual: `h1` の個数と見出しレベルの飛びを数える | 見出しテキストの品質、視覚的表現と構造の一致全般。**Visual 側は問題 3 件以上で fail、それ以外は必ず warning で、合格を出しません** |
| 1.3.2 意味のある順序 | A | **なし** | — | 全部 |
| 1.3.3 感覚的な特徴 | A | **なし** | — | 全部 |
| 1.3.4 表示の向き | AA | axe / Interactive | axe: `css-orientation-lock`（CSS で向きを固定していないか）。Interactive: portrait(375x667) と landscape(667x375) のスクリーンショットを撮影 | **Interactive 側は撮影するだけで、画像の比較も崩れ検出も行いません。pass も fail も返さず必ず warning です** |
| 1.3.5 入力目的の特定 | AA | axe / Visual | axe: `autocomplete-valid`（`autocomplete` が**書かれている場合に**その値が妥当か）。Visual: フォーム要素の有無 | **必要なフィールドに `autocomplete` が付いているかは検証していません。** Visual 側はフォームがあれば必ず warning、なければ「該当なし」で pass |
| 1.4.1 色の使用 | A | axe / AI | `link-in-text-block`（本文中リンクが色以外でも識別できるか） | 色以外で情報を伝えているかの全般的な判断 |
| 1.4.2 音声の制御 | A | axe / Visual | axe: `no-autoplay-audio`。Visual: `audio[autoplay]` / `video[autoplay]` の有無（0 件で pass、1 件以上で fail） | JS で再生を開始する音声。3 秒以上かどうかの判定。停止手段の有無 |
| 1.4.3 コントラスト（最低限） | AA | axe | `color-contrast` でテキストと背景のコントラスト比を計算 | 背景画像・グラデーション上のテキスト（axe が `incomplete` に倒す） |
| 1.4.4 テキストのサイズ変更 | AA | axe / Interactive | axe: `meta-viewport`（`user-scalable=no` 等でズームを禁止していないか **だけ**）。Interactive: `zoom: 2.0` を当て、`overflow: hidden` かつ `scrollHeight > clientHeight` の要素があれば fail | 200% でのテキストの重なり、横方向のはみ出し、可読性。**Interactive 側は fail か warning のみで、合格を出しません** |
| 1.4.5 文字画像 | AA | **なし** | — | 全部。AI が `<img>` から推測を試みる |
| 1.4.10 リフロー | AA | Interactive | ビューポートを 320x256px に変更し `documentElement.scrollWidth > clientWidth` を判定 | 横スクロールは出ないが内容が読めない・重なっている場合 |
| 1.4.11 非テキストのコントラスト | AA | Visual | `button` `input` `select` `textarea` `[role=button]` の**境界線と背景**のコントラスト比のみ | アイコン、グラフィック、状態表示、境界線のないコンポーネント。**問題 4 件以上で fail、それ以外は必ず warning で、合格を出しません** |
| 1.4.12 テキストの間隔 | AA | axe | `avoid-inline-spacing`（インラインスタイルで行間等を `!important` 固定していないか） | 実際に間隔を変更したときの表示崩れ |
| 1.4.13 ホバー又はフォーカスで表示されるコンテンツ | AA | **なし** | — | 全部 |

### 2. 操作可能

| 基準 | レベル | 判定担当 | 実際に検証していること | 検証していないこと |
|---|---|---|---|---|
| 2.1.1 キーボード | A | axe（間接的） | `frame-focusable-content` `scrollable-region-focusable` `server-side-image-map` の 3 ルールのみ | **「すべての機能がキーボードで操作できるか」を通しで確認する検査は存在しません。** この 3 ルールは達成基準のごく一部です（[既知の限界](#known-limits)参照） |
| 2.1.2 キーボードトラップなし | A | Interactive | Tab を繰り返し送出し、同一要素に 3 回連続で留まる／訪問カバレッジ 0.5 未満で循環が閉じる／最大反復まで閉じない を fail | **Shift+Tab（逆方向）は送出していません。** Esc での離脱可否も未検証 |
| 2.1.4 文字キーのショートカット | A | Visual | `accesskey` 属性と、CDP で取得した document/window の `keydown`/`keypress`/`keyup` リスナー | 検出されたショートカットに無効化・再設定・フォーカス時限定の手段があるか。**fail は返さず、検出されれば warning** |
| 2.2.1 タイミング調整可能 | A | axe / AI | `meta-refresh`（meta による自動更新） | JS のタイマー、セッションタイムアウト、延長手段の有無 |
| 2.2.2 一時停止、停止、非表示 | A | axe / AI | `blink` `marquee` | CSS アニメーション、カルーセル、自動スライダー、停止手段の有無 |

### 自動検査だけでは「確認OK」にならない 19 項目

次の基準は、自動検査（axe-core / Visual / Interactive）が存在しないか、存在しても合格を出さない設計のため、自動検査では「確認OK」になりません。生成 AI が証拠つきで判定するか、人が目視で確認する以外に埋まりません。

**自動検査が存在しない（16 項目）**

1.2.3 / 1.2.4 / 1.2.5 / 1.3.2 / 1.3.3 / 1.4.5 / 1.4.13 / 2.3.1 / 2.4.5 / 2.4.6 / 2.5.1 / 2.5.2 / 3.2.3 / 3.2.4 / 3.2.6 / 3.3.4

**検査はあるが、合格を出さない設計（3 項目）**

| 基準 | 合格を出さない理由 |
|---|---|
| 1.4.11 非テキストのコントラスト | フォーム部品の境界線しか測れず、アイコン・グラフィックを検証できないため |
| 2.4.7 フォーカスの可視化 | スタイルが変化することは分かっても、それが実際に見えるか（コントラスト・太さ）は分からないため |
| 4.1.3 ステータスメッセージ | 属性の存在は分かっても、メッセージが支援技術に伝わるかは分からないため |

このうち **2.3.1（閃光）、3.2.3 / 3.2.4 / 3.2.6（ページ間の一貫性）は、生成 AI でも実質的に埋まりません。** 前者は動画の再生と輝度変化の解析が必要で、後者は複数ページの比較が必要ですが、どちらもこのツールの検査範囲外だからです。人が確認するしかありません。

## 6. 意図的な設計判断

### 間違った合格は、間違った不合格よりはるかに悪い

不合格が間違っていれば、修正しようとした人が「これは問題ない」と気づきます。誤りは現場で止まります。

合格が間違っていれば、**誰もそのページを見ません。** 検査済みとして扱われ、実際に使えない人が残ります。誤りは利用者のところまで届きます。

この非対称性が、本ツールの設計判断のほぼすべての根拠です。

- 検証範囲が達成基準の一部にとどまる検査は、問題が見つからなくても合格を出さない（1.4.11 / 2.4.7 / 4.1.3、Visual の 1.3.1）
- CDP 接続に失敗した検査は、問題ゼロとして扱わず warning に倒す（2.1.4 / 2.5.4 / 2.5.7）
- 生成 AI が証拠を書けなかった判定は、機械的に未確認へ降格する
- 「不適合 → 適合」の上書きは、証拠がある場合しか通さない
- 「問題の可能性がある」程度の所見は fail にせず、warning として懸念点を残す

結果として **未確認の件数は多くなります。** 実測では、意図的に適合実装した検証用サイトでも「確認OK 23 / 修正あり 0 / 未確認 32」でした。これは検査の失敗ではなく、確認できていないことを確認できていないと表示している状態です。

### 一部しか確認できていない 17 項目を「確認OK」に丸めない

デジタル庁『ウェブアクセシビリティ導入ガイドブック』の基本 17 項目は、1 項目が複数の WCAG 達成基準に対応します。集約ルールは次の通りです（`generate-baseline-view.ts`）。

| 条件 | 表示 |
|---|---|
| 対応する達成基準に 1 つでも「不適合」がある | ❌ 要修正 |
| 不適合はないが「未確認」が残っている | ⚠️ **一部未確認** |
| 対応する達成基準がすべて「適合」 | ✅ 確認OK |
| 対応する達成基準がすべて A+AA の範囲外 | — 判定対象外 |

**「一部未確認」という状態をわざわざ設けているのは、丸めないためです。**

項目 6「キーボードだけで全機能にアクセスできる」は 2.1.1 / 2.4.3 / 2.4.7 / 3.2.1 / 3.2.2 の 5 基準に対応します。3 基準が適合でも 2 基準が未確認なら「⚠️ 一部未確認」と表示します。多数決や平均で「確認OK」に寄せることはしません。

なお 2.4.10（セクション見出し、Level AAA）と 4.1.1（構文解析、WCAG 2.2 で廃止）は「検査できなかった」のではなく「対象範囲の外」です。レポート上も区別して表示します。データの欠落と範囲外を混同しないためです。

### 決定性を優先する

同じ URL に対して何度実行しても同じ結果になることを優先しています。読み込み手順の固定、`prefers-reduced-motion` の強制、アニメーション duration の 0 秒固定、タイムゾーン・デバイススケール・配色の固定はすべてこのためです。生成 AI 側も「証拠を引用できなければ warning に倒す」ことで、判定のぶれを未確認側へ寄せています。

それでも対象サイトが実行ごとに違うコンテンツを返す場合（ランダムバナー・A/B テスト・広告）は結果が変わります。`--exclude` で該当要素を除外してください。

## 既知の限界 — 根拠の薄い「確認OK」が残る
<a id="known-limits"></a>

ここまで挙げた設計にもかかわらず、**根拠が達成基準のごく一部にしか及ばないのに「確認OK」と表示される場合があります。** 検証用サイトで実測して確認できたものを挙げます。

原因は共通です。統合が axe-core の結果を **WCAG タグ単位** で引き当てるため、その基準に紐づくルールが 1 つでも `passes` に入っていれば「適合」になります。そして専用検査が「合格とは言えない」と warning を返しても、warning は上書きしない仕様（第 3 章 (a)）のため、axe-core の「適合」がそのまま残ります。

| 基準 | 「確認OK」の根拠になっているもの | 実際には確認できていないこと |
|---|---|---|
| 1.4.4 テキストのサイズ変更 | axe `meta-viewport` が pass（ズームを禁止していない） | 200% 拡大時にテキストが読めるか。Interactive の専用検査は warning を返しているが上書きされない |
| 2.1.1 キーボード | axe `scrollable-region-focusable` 等が pass | すべての機能がキーボードで操作できるか。スクロール領域が 1 つ合格しただけで項目全体が適合になる |
| 1.3.5 入力目的の特定 | axe `autocomplete-valid` が pass | `autocomplete` が **1 つでも正しく書かれていれば** 適合になる。他のフィールドに `autocomplete` が無くても検出されない |
| 1.3.1 情報及び関係性 | axe `list` `listitem` 等が pass | 見出し階層。Visual の見出し検査は warning を返しているが上書きされない |
| 3.3.2 ラベル又は説明 | axe `form-field-multiple-labels` が pass（ラベルが重複していない） | ラベルが存在するか・説明として適切か |
| 1.2.2 キャプション（収録済） | axe `video-caption` が pass（`<track kind="captions">` がある） | キャプションの内容・正確さ・同期。トラックが 1 つ宣言されていれば適合になる |

いずれも実測で再現を確認しています。たとえば `<input type="email" autocomplete="email">` と `<input type="tel">`（autocomplete なし）を並べたページでは、1.3.5 が「確認OK」になります。1.2.2 は、`<track>` の参照先ファイルが存在しなくても「確認OK」になります。

**これらの項目については、レポートの「確認OK」を額面どおり受け取らないでください。** 表示上「自動判定」となっている項目の根拠は、Excel・Markdown レポートの備考列で確認できます。
