# a11y-shiken

[![CI](https://github.com/taichiyam/a11y-shiken/actions/workflows/ci.yml/badge.svg)](https://github.com/taichiyam/a11y-shiken/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](LICENSE)

**アクセシビリティの確認は「何から手をつけるか」で止まります。**

URL を渡すと、[axe-core](https://github.com/dequelabs/axe-core) と Playwright、それに生成 AI で WCAG 2.2 Level A + AA の **55 項目**を検査し、
結果をデジタル庁『ウェブアクセシビリティ導入ガイドブック』の **基本17項目**に集約して返す Claude Code スキルです。
55 行の表ではなく「まずどこを直すか」から読める形にします。

出力は 2 つ。ディレクターには Excel のチェックシート、開発者には HTML スニペットと推奨対応つきの Markdown。
同じ検査結果を、それぞれが次に使える形で出します。

そして **確認できなかったものを「確認OK」に混ぜません。** 機械で判定しきれない項目は「未確認」として残り、
17 項目に集約するときも「一部未確認」のまま表示されます。未確認の件数は多くなりますが、
それは検査の失敗ではなく、確認できていない範囲がそのまま見えている状態です。

**English**: a11y-shiken is a Claude Code skill that audits a web page against WCAG 2.2 Level A + AA (55 success criteria)
with axe-core, Playwright, and an LLM, then rolls the results up into the 17 baseline items of the Japanese Digital Agency's
web accessibility guidebook, emitting an Excel checklist and Markdown reports (Japanese output only).
Its governing rule is that a false pass is far worse than a false failure: an LLM verdict that provides no evidence text
is demoted to "unverified" by the merge script rather than by prompt instruction (the script checks that evidence is present,
not that it is genuine — a fabricated quote would still pass this gate),
an axe-core pass on a criterion its rules only partially cover is recorded as unverified instead of as conformance,
and a baseline item is never rounded up to "OK" while any of its criteria remain unverified. It reports; it does not auto-fix.

> ## ⚠️ v0.1.0 — ベータ版です
>
> - **正式なアクセシビリティ試験（JIS X 8341-3:2016）の代替にはなりません。** 適合表明の根拠には使わないでください
> - **55 項目のうち一部は生成 AI が判定しています。その精度は自前の検証サイトでしか測っていません**（[精度の実測](#精度の実測) / [制限事項](#制限事項)）
> - HTML のみを対象とします。**PDF・動画・音声は検査できません**
> - 出力・オプション・ファイル構成は、今後の版で変わる可能性があります

## 設計思想

### 1. 間違った合格を生まない

不合格が間違っていれば、修正しようとした人が「これは問題ない」と気づきます。誤りは現場で止まります。

合格が間違っていれば、**誰もそのページを見ません。** 検査済みとして扱われ、実際に使えない人が残ります。誤りは利用者のところまで届きます。

**間違った合格は、間違った不合格よりはるかに悪い。** この非対称性が、このツールの設計判断のほぼすべての根拠です。

そのため次の 3 つを、**プロンプトの指示ではなく統合スクリプトの分岐**として実装しています。
生成 AI が指示を無視して証拠なしの合格を出しても、最終結果には反映されません。

| ガード | 内容 |
|---|---|
| **証拠必須ガード** | 生成 AI の「適合」「不適合」「該当なし」のうち、証拠（アクセシビリティツリーや HTML から引ける記述）が空のものを機械的に「未確認」へ降格する。「このページに動画はありません」のような該当なし判定にも同じく証拠を要求する |
| **「適合」への上書き制限** | 機械検査の結果を生成 AI が「適合」で上書きするのは、証拠がある場合しか通さない。証拠つきで判定が食い違ったときは、上書きしたうえで矛盾として記録に残す |
| **カバレッジガード** | axe-core の pass を適合の根拠にしてよいかを、達成基準ごとに監査して決めている。基準の一部の条件しか見ていないルールの pass は、適合ではなく「未確認」に倒す（現時点では 55 項目すべてがこの扱い）。不適合の検出力は落としません |

これとは別に、**検証範囲が達成基準の一部にとどまる専用検査**（フォーカスの可視化、非テキストのコントラスト、ステータスメッセージなど）も、
問題が見つからなかったことを合格の根拠にしません。逆に、Visual / Interactive / 生成 AI が**証拠つきで出した合格は「適合」になります。**
上のガードが止めているのは「根拠が基準のごく一部にしか及ばない合格」であって、合格そのものではありません。

同じ理由から、**検出した問題を自動で修正する機能は持ちません。** 直し方の提案はレポートに書きますが、
適用するかどうかの判断は人に残します。判定を保守側に倒す設計と、コードを自動で書き換える機能は相性が悪いためです。

なお証拠必須ガードが検査しているのは「証拠が**書かれている**こと」であって、「証拠が**正しい**こと」ではありません（[制限事項](#制限事項)）。

判定と統合のルールは [判定の仕組みの詳細](docs/how-it-works.md) に、達成基準ごとに「何を検証していて、何を検証していないか」まで書いてあります。

### 2. 優先順位を示す — 基本17項目への集約

WCAG 2.2 の 55 項目を渡されても、どれが致命的でどれが後回しでよいのかは判断できません。

デジタル庁『ウェブアクセシビリティ導入ガイドブック』は、この問いに公式の答えを出しています。

| | |
|---|---|
| **重大（非干渉）4項目** | できていないと、利用者がページの**他の部分にもアクセスできなくなる** |
| **必須13項目** | 満たしていないと、内容が十分に伝わらない／操作が不完全にしかできない |

このツールは、55 項目の判定結果をこの **17 項目に集約**して提示します。

```
| # | 項目                                 | 状態          | 内訳                        |
|---|--------------------------------------|---------------|-----------------------------|
| 2 | 袋小路に陥らせない（キーボードトラップ） | ❌ 要修正      | 1基準中 不適合 1             |
| 6 | キーボードだけで全機能にアクセスできる    | ⚠️ 一部未確認  | 5基準中 確認 3 / 未確認 2    |
```

集約のとき、**一部しか確認できていない項目を「確認OK」に丸めません。**

| 条件 | 表示 |
|---|---|
| 対応する達成基準に 1 つでも「不適合」がある | ❌ 要修正 |
| 不適合はないが「未確認」が残っている | ⚠️ **一部未確認** |
| 対応する判定対象内の達成基準がすべて「適合」 | ✅ 確認OK |

（2.4.10（Level AAA）と 4.1.1（WCAG 2.2 で廃止）は判定対象外として集約から除外されます）

項目6「キーボードだけで全機能にアクセスできる」は 5 つの達成基準に対応します。
**3 基準が適合でも、2 基準が目視未確認なら「⚠️ 一部未確認」と表示します。** 多数決や平均で「確認OK」に寄せることはしません。

出典: [ウェブアクセシビリティ導入ガイドブック](https://www.digital.go.jp/resources/introduction-to-web-accessibility-guidebook)（デジタル庁）
本ツールはデジタル庁・WAIC・W3C・JISC の認証や推奨を受けたものではありません。

## 精度の実測

生成 AI の判定がどれくらい当たるのかを、正解を仕込んだ自前の検証サイト 4 ページに対して、
**正解を伏せた盲検**で、会話文脈を持たない**独立した 3 セッション**に判定させて実測しました。

| 指標 | この盲検プロトコルでの実測値 |
|---|---|
| 既知の仕込み違反を「合格」にした数 | **0 件 / 8 件**（3 セッションとも同じ 8 件が対象。危険側に倒れる機会があったのはこの 8 件で、残り **13 件 / 21 は判定自体が出ていない**） |
| 生成 AI が判定を試みた範囲 | 55 項目中 **15 〜 16 項目**（各セッション・1 ページあたり） |
| 検出 | 判定を試みた **8 件は 3 セッションとも不適合**。正解の違反にあたるセルは 3 体が **100% 一致** |
| 証拠の幻覚（実在しない要素の引用） | **0 件 / 173 判定**（3 セッション合計） |

**「間違えない」のは「判定できることしか判定しない」ことの裏返しです。**
正解の違反 21 件のうち 13 件は、そもそも判定の対象になりませんでした。
機械検査と統合した最終的なチェックシートで「修正あり」になるのは 21 件中 14 件です。

なお、上のガードのうち**証拠必須ガードと「適合」への上書き制限**は、この測定では 1 件も作動していません
（生成 AI の判定 173 件すべてに証拠が付いていたため）。**この実測は、この 2 つのガードが効くことを実証したものではありません。**
レポートが監査したのもこの 2 つ（と判定矛盾フラグ）で、カバレッジガードは監査の対象外です。

そして数値はいずれも、**特定の盲検プロトコルという条件下で観測されたもの**です。
本番のパイプラインは生成 AI に渡す入力が異なり、実サイトでは測っていません。
**製品一般の性能としてそのまま引用できる数値ではありません。**
測定条件・限界・判定者 3 体の生データは [精度実測レポート](docs/accuracy-report.md) にあります。

## インストール

npm には公開していません。GitHub リポジトリから直接導入します。

### 1. `npx skills add`（推奨）

```bash
# プロジェクトに入れる
npx skills add taichiyam/a11y-shiken

# 自分の環境すべてで使う（ユーザーレベル）
npx skills add taichiyam/a11y-shiken --global
```

このリポジトリの `skills/a11y-shiken/` を読み取り、エージェントのスキルディレクトリに配置します。
インストール後、Claude Code で `/a11y-shiken` と入力すると起動します。

### 2. Claude Code plugin marketplace

`/plugin` で更新まで管理したい場合はこちらを使います。

```
/plugin marketplace add taichiyam/a11y-shiken
/plugin install a11y-shiken@a11y-shiken
```

プラグイン経由で入れた場合、起動は `/a11y-shiken:a11y-shiken` になります（プラグイン名で名前空間が付くため）。

## 使い方

```
/a11y-shiken https://example.com
```

複数ページをまとめて検査するときは、`ラベル,URL` 形式の CSV を渡します。

```csv
TOP,https://example.com/
会社概要,https://example.com/about/
```

```
/a11y-shiken urls.csv
```

### 出てくるもの

```
docs/a11y-test/{日時}_{ドメイン}/
├── report/
│   ├── a11y-checklist-{ドメイン}-{日付}.xlsx   ← 55 行のチェックシート
│   ├── index.html                              ← サイドバー付き HTML ビューア
│   └── markdown/
│       ├── {ページ}.md                          ← HTML スニペット・推奨対応つき
│       └── {ページ}-baseline-17.md              ← 基本17項目ビュー
└── data/                                        ← 生 JSON・スクリーンショット（証跡）
```

実際の出力は [examples/komaru/](examples/komaru/) を参照してください。
同じサイトの壊れた版と直った版を検査した実測結果と、生成された Excel チェックシートが置いてあります。

## 何をどう判定しているか

55 項目を、判定方法で 3 つに分けています。

| 種別 | 判定 |
|---|---|
| 🤖 **自動チェック** | [axe-core](https://github.com/dequelabs/axe-core) で検出 |
| 🔄 **部分自動チェック** | axe-core で一部検出したうえで、目視確認が必要 |
| 👁 **目視確認** | 人が判断します |

このうち、**リンクテキストが目的を説明しているかなど、文脈がないと判定できない項目**は、
レンダリング後のアクセシビリティツリーと HTML を生成 AI が読んで判定します。

**証拠となる箇所を引用できないときは、合格にせず「未確認」に倒します。**

達成基準ごとの担当検査と、統合したときにどう 3 値が決まるかは [判定の仕組みの詳細](docs/how-it-works.md) にまとめてあります。

## 制限事項

**このツールが「できないこと」を先に書きます。**

- **正式な試験の代替になりません。** JIS X 8341-3:2016 に基づく試験は人が実施する必要があります
- **生成 AI の判定精度は、自前のダミーサイト 4 ページでしか実測していません。** [精度の実測](#精度の実測)に挙げた値は特定の盲検プロトコルの条件下で観測されたもので、**実サイトでは測っていないため、そのまま実サイトの精度にはなりません。** また **「間違えない」のは「判定できることしか判定しない」ことの裏返し**であり、盲検では生成 AI が判定を試みたのは 55 項目中 15 〜 16 項目にとどまりました（[精度実測レポート](docs/accuracy-report.md)）
- **証拠は「書かれていること」しか検査していません。** 生成 AI が実在しないセレクタを証拠として書いた場合、証拠必須ガードは素通りします（上記の盲検では幻覚 0 件でしたが、仕組みとして防いではいません）
- **HTML のみが対象です。** PDF・動画・音声・埋め込みコンテンツは検査できません
- **55 項目すべてが自動で埋まるわけではありません。** 目視確認が必要な項目は「未確認」として残ります
- **検査は 1 ページ単位です。** ページ間の一貫性を見る達成基準（3.2.3 / 3.2.4 / 3.2.6）は埋まりません
- Basic 認証つきの環境・自己署名証明書の環境には、現時点で対応していません

## 外部への送信について

**一部の判定で、検査対象ページの HTML とアクセシビリティツリーを Anthropic の API に送信します。**

Claude Code を通じて動作するため、生成 AI が判定する項目については対象ページの内容が API に送られます。
axe-core・Playwright による自動チェックは、すべて手元で完結します。

**外部に出せないコンテンツを扱う場合は、この点をご確認のうえご利用ください。**
